# 真歌电音事故：证据与反例

## 本次最终结论

2026-09-27，用户提供 MP3，经本机转为 stereo E-AC-3，通过 SDA 解码与 HRTF 渲染在 MuMu 播放。表现为持续电音、原音乐隐约可辨。修复提交 `ed742f8` 后用户明确反馈“可以了！！！”，该歌曲用例听感通过。

### 确认的问题

1. **AAudio 格式错配**：手写 `PCM_FLOAT=1`，但 NDK `1=PCM_I16`、`2=PCM_FLOAT`。向整数流交付 f32 原始字节，样本位模式被错误解释。现在使用 ndk-sys 并校验授予格式。
2. **诊断工具损坏数据**：WavDump 的 `popped` 是帧数，复制 `block[..popped]` 只保存一半 stereo 数据。应为 `block[..popped*2]`；消费时钟仍加 `popped`。旧 WAV 的失真不能用来指责渲染器。
3. **旧 callback FFI 错误**：要求函数指针的 API 被声明为结构体指针。数据段执行崩溃与此吻合，不是“MuMu 回调模式必崩”的证据。没有完成修正 callback 路径后的独立设备复测，不能泛化支持性结论。
4. **验证假阳性**：忽略测试显示 `0 passed / 1 ignored` 却曾被报为通过；只 cargo check 后拷贝旧 so；编译输出经管道筛选掩盖 exit code；没有 APK hash/版本标记；听到电音被误当成测试信号正常。

### 有效证据

详见项目 `docs/android-pcm-format-validation.md`：

- NDK 实际枚举与声明；设备实际日志 `format=2(PCM_FLOAT)`、sample_bytes=4、frame_bytes=8、channels=2、rate=48000。
- 2051 帧 stereo 导出逐样本回归，包含尾块，长度与通道均正确。
- 本机整曲 10,142,208 帧，211.296 秒；解码和消费帧数一致，无 rejection。
- 独立 FFmpeg/SDA 解码的前 64 秒包络相关性约 0.9999999935；正确导出后的渲染包络相关性约 0.9775（对齐 50ms）。相关性是辅助，不是听感验收的替代品。
- 修复 APK 的 `.so` 摘要核验及 MuMu 前约 20 秒静音验证，xruns=0。
- 设备掉线后重新安装修复版，用户最终确认正常。未测得 MuMu 整曲完成日志，不补造此项结果。

## 应撤回的历史判断

| 历史说法 | 为什么不成立 | 正确做法 |
| --- | --- | --- |
| “电音就是测试语料音色，已验收” | 用户一直在报告听不清原曲 | 保留失败状态，等明确听感确认 |
| “Android 12 / MuMu 音频栈坏了” | 存在可直接解释崩溃/噪音的 FFI 与枚举错误 | 先核对 NDK 签名和真实格式 |
| “峰值 1.05 就解释持续电噪声” | 峰值不能描述失真分布；格式错配未排除 | 测削波比例并做独立解码对照 |
| “5.1 通道 1 是右声道，右声道全零” | 声道顺序需要标签，不能按下标猜 L/R/C | 输出每通道标签、能量和布局 |
| “低峰值说明解码干净” | 低幅噪声也可能听不清音乐 | 与同一码流的独立参考解码对照 |
| “相关性 0.376 证明 HRTF 污染” | 导出丢半块、窗单位不对、时序没对齐 | 先验证测量工具和数据完整性 |
| “一个正弦通过证明整个渲染正常” | 没覆盖真实输入、声床、输出格式 | 分层验证同一真实素材 |
| “不加载 HRTF 是旁路实验” | 当前引擎直接输出静音且不推进同一路径 | 使用恒等 IR 或明确旁路 |
| “默认 VBAP 空、必须补 SetLayout” | 当前 `new()` 默认 7.1.4 | 读初始化实现再改行为 |
| “coverage 可返回数万帧导致 FIFO 溢出” | 调用已有 DEFAULT_PARTITION 上限 | 核对真实边界，不按日志猜逻辑 |
| “数字一直涨、pid 存活等于音频正确” | 可能只在提交，或进程处于异常状态 | 看消费帧数、拒绝、输出格式与听感 |

## 三个回归式任务示例

这些用于检查 skill 是否指导正确，不自动启动音频或改环境。新会话可用 `/sda-android-audio-debugging` 触发。

### 场景 A：持续电音

**输入**：“MuMu 上歌只有电音，能隐约听到人声，进度一直涨。继续查，别让我换系统。”

**期望行为**：先停止测试音，核对 NDK 枚举/实际 format 与写入类型、JNI ABI、APK 版本；不以低音量或高相关性替代输出格式校验。不宣称用户听到的是正常电子测试音。

### 场景 B：WAV 长度只有一半

**输入**：“pop_into_f32 返回 1024，我复制 block[..1024]，WAV 大概只有一半长。是不是时钟也要乘 2？”

**期望行为**：1024 帧 stereo 对应 2048 个样本，复制范围应乘 2；codec 消费时钟加 1024 即正确。100ms i16 stereo 窗口为 19200 字节。添加尾块/逐样本验证。

### 场景 C：构建失败却安装成功

**输入**：“cargo check 是绿的，刚改的 decodedSamplePos 在 logcat 还是没有，Gradle 打包安装也成功了。”

**期望行为**：检查真实 cargo build、工具链目标、CARGO_TARGET_DIR、staged/包内/设备产物标识；失败即停止，不继续 cp 和安装。保持固定 MuMu serial，不启动官方 AVD；验证后让用户手动低音量试听。

## 输出尺度

报告“已证实/已修复”“本机验证”“设备验证”“用户听感”“未覆盖”即可。避免每发现一个线索就喊最终根因。没有用户操作需求时继续已授权工作；设备连接被拒绝、听感判定等真正依赖用户的步骤才交回。
