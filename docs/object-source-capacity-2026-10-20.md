# 解码后独立源容量：128 路

截图的错误来自 AC-4 Full A-JOC 数值重建层：`num_umx_signals=24` 被上游产品边界 `MAX_RECONSTRUCTED_OBJECTS=20` 拒绝。并非声卡或最终双声道输出通道不足。SDA 对解码后的独立源统一采用 128 路上限，声床、LFE、对象共同计数；最终耳机输出仍是双声道。

## 改动

- 在 MIT 许可的固定上游版本 a23965312a53d3cfb1a63cbae692a788efe46123 基础上保留 AC-4 decode crate 本地副本。重建凭证、矩阵、差分、rolling 状态及终端拓扑统一使用 128 边界；大工作区仍在堆上。输入/downmix、规范表验证、IMS 与其他未支持语法边界不变。允许 128 个无 LFE 对象，或在应用总路数上限内保留独立 LFE；不把第 129 路截掉冒充成功。
- Audio Vivid 的传输转逻辑场景上限由 64 改为 128。编码传输通道、HOA 和动态元数据原有位宽保持不变；多个逻辑对象可引用合法传输通道。不会把编码头里的 16 随意改成 128。
- MPEG-H 的准备目录统一扩大源、OAM、元素与 DRC 通道存储，包括重复定义；保留已支持 codec profile/level 对声床与 HOA 的约束。C PCM/元数据捕获、Rust、TypeScript、iOS source bridge 均支持最多 128 路。
- C 捕获越界有显式错误状态，PCM/元数据超限、非法编号和非法尺寸会向上报告；不再静默丢掉元数据或表现为没有新帧。每源最多 16 条捕获记录，128 源对应 2048 条。
- 所有格式共用 FrameData 的源数检查与 FrameRouter。保留零 PCM 的元数据帧行为。渲染器原有 128 源上限不变，原生命令队列容纳满额场景声明/退休命令及其 PCM 批次。

E-AC-3 JOC 的编码语法和重建算法没有扩展位宽；其合法输出进入同一个 128 路通道映射与原生链路。容量上限不是承诺每种编码/profile 都能在码流里声明 128 路。

## 验证

- AC-4 重建库：630 通过、4 原有忽略。非零输入下分别重建 24/64/128 个不同系数的输出，并逐路核对复数 QMF；覆盖终端映射、LFE 插回、129 拒绝、reset 与事务状态。
- Core：47 通过、1 原有忽略。包含 Audio Vivid 24/64/128 个逻辑输出的 PCM/元数据/唯一对象 ID 与 129 拒绝；既有有效 AC-4 编码夹具继续通过。
- Native：112 通过、4 原有忽略。四种格式的 128 路映射及 129 拒绝；在 128 路里分别仅使第 1 与第 128 路发声，空间平衡开/关都经过实际 HRTF 和输出 FIFO，输出电平差小于 0.01 dB。
- 真正 C 捕获桥：使用逐路标记 PCM 和逐对象元数据验证 24/64/128 路、2048 条记录、越界与 reset。此测试隔离了解码器 API，不能冒充真实 MPEG-H 128 路曲目解码。
- 主机 C 栈使用报告已检查，最大函数帧为 44720 字节，MHAS 为 22048 字节；这是主机编译器的测量，不冒充 Apple 设备编译器结果；按用户后续要求，纯打包工作流不再运行测试。

截图曲目的原始 AC-4 文件未提供，本地不声称已经对该首真实 24 路曲目完成试听；测试音乐、PCM 不上传，测试夹具不进入真机资源。Windows/macOS 打包必须从同一提交重建 core/WASM 与原生库。

TypeScript 捕获适配器也逐路验证了 24/64/128 路 PCM/元数据，以及 129 路和无 PCM 帧时的显式捕获错误。
