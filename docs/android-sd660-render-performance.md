# Android 渲染吞吐与后台空间视图修复（2026-10-22）

目标来自 `0c09dc0` 的真实手机诊断：用户确认小米 Note 3 / 骁龙 660，48 kHz、15 个连续对象、E-AC-3/JOC、空间平衡开启。44.028 秒采样中，每个 1024 帧块平均渲染 34.017 ms，而块时长只有 21.333 ms；软件回调欠供增加 16.602 秒对应的输出帧，硬件 xrun 为零。解码已领先约四秒，因此重点是渲染吞吐与 CPU 争用。

修复内容：

- 连续对象 HRTF 在 Android 使用与对象混音、虚拟音箱和直接对象相同的调用线程参与执行器。渲染协调线程参与实际卷积，避免将整个阶段交给工作池后等待。
- 至少八个对象时，Android DSP 参与者按可用 CPU 数量限制为最多三个（协调线程加最多两个辅助线程）；小场景继续内联执行。没有更改 iOS 的线程预算。
- CPU 配额在启动阶段预热；播放期间由现有的一秒媒体控制轮询在引擎锁之外更新；渲染阶段只读取原子缓存。避免在每个混音/卷积阶段重复执行可能涉及操作系统配额或亲和性查询的探测（具体开销依平台实现而定）。控制线程会更新预算以跟随运行期配额变化，诊断 `input.dspCpuBudget` 可查看最近结果。
- 空间平衡的能量滤波器仍逐样本推进；只将未被使用的逐样本 dB 目标计算延至真正消费它的块/开关边界。方向强度仍按相同公式逐样本平滑。测试包含块内切换和三个采样率。
- 真峰值检测保留原有 193-tap FIR、阈值、lookahead、声道联动和累加顺序。ARM64 用 NEON 并行计算互不依赖的相位；x86_64 使用 SSE2。没有缩短滤波器或采用近似峰值。
- 已稳定的单位距离包络跳过恒等运算。单位耳机补偿用相同块边界的直接拷贝代替恒等 FFT，保持延迟；从未激发的扩散延迟线仅推进原时钟，首次信号和后续尾音与原实现一致。
- Android 空间页原先只在 iOS 实施隐藏/后台停绘。现在两端都根据页面可见性和 AppState 停止隐藏的 3D 循环，返回复用场景、相机和资源。前台可见空间页保持原渲染方式。
- 现有只读远程诊断增加 `graphics.sceneLoopRequested`，并将此标志写入历史样本；事件含 `scene-render-start` / `scene-render-stop`。该值表示 JS 请求的绘制状态，不是实际 GPU 帧率。

声音与性能验证：

- 55 项相关主机 DSP 回归通过，涵盖真峰值、控制目标、前方保护、低频、左右对称、空间开关、耳机补偿转换和扩散器首次激发。
- 向量真峰值检测及限幅包络与标量参考逐样本、逐位相同；延迟求值与逐样本参考在块和块内开关边界结果相同。
- 使用当前接受的 HRTF、同输入和 Android 调度策略，固定/移动 15 对象 E-AC-3、15 对象 MPEG-H、32 对象 Audio Vivid 四组主机基准平均耗时下降约 28%–36%。这些是同一主机上的对照，不是骁龙 660 的实测耗时。
- 完整场景 PCM 最大差值约 `4.7e-9`，差异能量低于原信号约 130 dB，整体能量变化小于 `0.000001 dB`。多线程分组求和与恒等 FFT 旁路的浮点舍入可以产生这种量级差异。
- 后台轮询与实际空间视图生命周期代码检查通过；恢复可见时继续原场景，不重建资源。

仍需在安装新包后，通过同一手机和相同场景读取远程诊断，比较每块渲染耗时、软件欠供增量、缓冲量及隐藏场景状态。不能用主机基准声称骁龙 660 已经消除卡顿。


## 锁屏供音与异构 CPU 调度（2026-10-22）

真机锁屏时媒体前台服务和 PARTIAL_WAKE_LOCK 均保持，未产生新崩溃；输出 FIFO 反复见底，音频时钟低于实时速度，媒体进度调用又长时间等待 nativeFeed 释放锁。

- Android DSP 使用同一有界线程池中的共享任务队列，每次领取一个独立源；快线程可接手剩余工作，避免调用线程固定持有三分之一任务。最终混音次序和处理精度不变。
- 音频线程按当前允许 CPU 与公开 cpu_capacity 选择高性能组，缺失时尝试最大频率；同构、信息不可读、较快 CPU 少于两个或系统限制时保持系统调度。没有机型白名单、root 或全局频率修改。
- 仅在音频线程初始化及控制面刷新时查询/设置 affinity。活动切换后和既有 1 Hz 媒体控制检查重新应用，以应对系统 cpuset 迁移覆盖线程选择；退出/改名线程从登记中移除。
- 解码线程同样使用此策略。压缩流读取批次由 24 KiB 缩小为 4 KiB，减少单次持有解码锁的时间。
- 媒体服务进度读取每次播放独立的不可变快照，由解码循环发布；读取不再等待解码锁。旧播放会话不能污染新会话的快照。

真机在核心热插拔状态下可能只允许两个高频核心。调度选择接受两个核心，并把 DSP 参与数限制在当前可用高频核心数之内，避免将两个高频核心误判为不可用，或让三个 DSP 执行者挤在两个核心上。

官方参考与方案依据：
- https://source.android.com/docs/core/audio/avoiding_pi ：避免优先级反转；优先状态复制与非阻塞 SPSC FIFO；加大缓冲不能代替定位锁竞争。
- https://developer.android.com/games/sdk/oboe/low-latency-audio ：回调避免锁、分配和 I/O；实际流参数与缓冲需要验证。
- https://developer.android.com/reference/android/os/PerformanceHintManager ：关联线程组的目标耗时提示，支持与否由设备决定，不能把 API 存在当成已经获得性能保障。此轮尚未启用 PerformanceHintManager。
